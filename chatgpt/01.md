> When copying and pasting data from clipboard, how are things like tables stored? Say I have a table in a webkit view, and I'm using Wails to create Go bindings, and I want to copy a table in the webview but paste it into Slack as a table rather than text, how would you tell the OS that it's tabulated data rather than text or an image?

The key point is that the clipboard doesn't generally contain a single piece of data with a flag saying "this is a table". It can contain **multiple representations of the same copied content**, each identified by a MIME type / platform clipboard type.

For a table copied from a browser, you'd commonly get something conceptually like:

```text
text/plain
text/html
```

For example, copying:

| Name | Age |
|---|---:|
| Alice | 30 |
| Bob | 42 |

might put these two representations on the clipboard.

**`text/plain`:**

```text
Name    Age
Alice   30
Bob     42
```

where those separators are usually tabs.

**`text/html`:**

```html
<table>
  <tr><th>Name</th><th>Age</th></tr>
  <tr><td>Alice</td><td>30</td></tr>
  <tr><td>Bob</td><td>42</td></tr>
</table>
```

The receiving application decides which representation it understands and prefers.

### For WebKit → Wails → Slack

If you're trying to make Slack recognise the structure, the interesting representation is probably **HTML**, not some special generic "table" clipboard format.

From JavaScript in your WebKit view you can explicitly write both:

```js
const html = `
<table>
  <tr><th>Name</th><th>Age</th></tr>
  <tr><td>Alice</td><td>30</td></tr>
  <tr><td>Bob</td><td>42</td></tr>
</table>`;

const text =
    "Name\tAge\n" +
    "Alice\t30\n" +
    "Bob\t42";

await navigator.clipboard.write([
    new ClipboardItem({
        "text/plain": new Blob([text], { type: "text/plain" }),
        "text/html": new Blob([html], { type: "text/html" })
    })
]);
```

Then when the user pastes, Slack can ask the OS clipboard for the formats it supports. If it supports `text/html`, it gets the `<table>` representation; otherwise it can fall back to `text/plain`.

### At the OS level

This is implemented differently on each platform.

On **macOS**, `NSPasteboard` holds multiple pasteboard types. Modern macOS uses UTIs such as:

```text
public.utf8-plain-text
public.html
public.rtf
public.png
```

Conceptually you'd do something like:

```objc
NSPasteboard *pb = [NSPasteboard generalPasteboard];

[pb clearContents];

[pb setString:plainText
      forType:NSPasteboardTypeString];

[pb setString:html
      forType:NSPasteboardTypeHTML];
```

So you're effectively saying:

> Here's the plain-text version of this thing, and here's the HTML version of the same thing.

Slack then chooses whichever it wants.

On **Windows**, the equivalent formats are typically:

```text
CF_UNICODETEXT
HTML Format
```

and Linux clipboard systems have equivalents such as:

```text
text/plain;charset=utf-8
text/html
```

### There's usually no "table" clipboard type

That's an important distinction.

You normally **don't** tell the OS:

```text
type = table
```

Instead you tell it:

```text
text/plain → tab-delimited representation

text/html →
<table>
   ...
</table>
```

Applications infer the semantic structure from the richer representation.

Excel/Numbers/etc. may additionally put proprietary formats onto the clipboard, but HTML is the normal interoperable mechanism.

### One complication: Slack

Whether this actually becomes a **Slack table** depends on what Slack's paste handler recognises.

Slack's editor doesn't simply display arbitrary pasted HTML. It parses/sanitises clipboard content and converts supported HTML structures into Slack's internal rich-text representation. So putting `<table>` on the clipboard is necessary for applications that support HTML tables, but **it doesn't guarantee Slack will convert `<table>` into its native table block**.

This is easy to investigate on your Mac. Copy a table from Safari/Chrome or Excel and inspect the pasteboard types:

```bash
osascript -e 'the clipboard as record'
```

Or, more usefully for your Wails/Go project, you could query `NSPasteboard` and dump **all available pasteboard UTIs** after copying a table from something that Slack successfully recognises. That would tell you exactly what WebKit/Excel/etc. is placing there.

> Is there any documentation regarding how to insert formatted data into Slack such as a table? Ideally via pasting from clipboard.

Yes. Slack now has substantially better support for actual tables than it used to, but there are **two different mechanisms** to distinguish: Slack's programmatic message format and what its desktop/Web client accepts from the OS clipboard.

Slack added a proper Block Kit `table` block in August 2025. It supports up to 100 rows × 20 columns, with cells containing plain text, numbers, or Slack `rich_text` (including bold, links, mentions, emoji, etc.). [Slack Developer Docs](https://docs.slack.dev/reference/block-kit/blocks/table-block?utm_source=chatgpt.com) Slack also added Markdown tables to its newer `markdown` block, so an app can submit ordinary Markdown table syntax and have Slack render it as a table. [Slack Developer Docs](https://docs.slack.dev/reference/block-kit/blocks/markdown-block/?utm_source=chatgpt.com)

The relevant official docs are:

- [Slack Table Block documentation](https://docs.slack.dev/reference/block-kit/blocks/table-block?utm_source=chatgpt.com) — the native structured table representation.
- [Slack Markdown Block documentation](https://docs.slack.dev/reference/block-kit/blocks/markdown-block/?utm_source=chatgpt.com) — includes Markdown table support.
- [Slack Rich Text documentation](https://docs.slack.dev/reference/block-kit/blocks/rich-text-block/?utm_source=chatgpt.com) — particularly interesting because Slack says this is also the representation produced by its WYSIWYG message composer.
- [Slack message formatting documentation](https://docs.slack.dev/messaging/formatting-message-text/?utm_source=chatgpt.com) — general formatting rules.

### But clipboard pasting is different

For your specific case — **Wails/WebKit → clipboard → Slack composer** — I can't find an official Slack document specifying a public clipboard interchange format such as:

> Put MIME type `application/x-slack-table` on the clipboard and Slack will turn it into a table.

The Block Kit JSON isn't a clipboard format; it's an API message format.

What *is* particularly interesting is that Slack's documentation explicitly says that the `rich_text` block is **the output of Slack's WYSIWYG message composer**. [Slack Developer Docs](https://docs.slack.dev/reference/block-kit/blocks/rich-text-block/?utm_source=chatgpt.com) That tells us what Slack ultimately represents formatted user messages as internally, but it doesn't document how Slack converts clipboard flavours into that representation.

For your application, I'd investigate the standard clipboard flavours Slack consumes. On macOS/WebKit, the important candidates are effectively:

```text

text/html
```

For a copied HTML table, you'd ideally put **both** representations on the clipboard:

```html
<table>
  <tr>
    <th>Name</th>
    <th>Status</th>
  </tr>

    <td><strong>Healthy</strong></td>

plus a `text/plain` fallback such as TSV:

API         Healthy

The key question is then whether **Slack recognises `text/html` containing `<table>` during a paste and converts it into its new table representation**. Slack's API documentation doesn't appear to specify that behaviour.

And there's a useful distinction from our previous discussion: putting TSV on the clipboard tells applications that understand spreadsheet-like pasted text where the cells are, but **there isn't an OS-level "this is tabular data" clipboard semantic** that automatically makes Slack create a table. HTML is much more likely to preserve the structural information.

> Can you search the web to see if there's any blogs, FAQs or user submitted comments anywhere that suggests mime types that Slack support when pasting from clipboard

There’s a fairly convincing body of reverse-engineered evidence. Slack doesn’t publicly document its clipboard protocol, but several independent projects have worked it out.

The most interesting MIME/type candidates are:

| Clipboard type | Evidence | What Slack appears to do |
|---|---|---|
| `slack/texty` | Strong, reverse-engineered | **Slack's native rich-text clipboard format** |
| `text/html` | Strong | Imports ordinary rich text into the composer |
| `text/plain` | Strong | Plain-text fallback; apparently important even when HTML is supplied |
| `org.chromium.web-custom-data` | Strong on macOS/Electron | Chromium container which can carry `slack/texty` |
| `public.html` | macOS UTI | macOS representation corresponding to HTML |
| `public.utf8-plain-text` | macOS UTI | macOS plain-text representation |

### `slack/texty` is probably what you're looking for

The most significant find is:

```text
slack/texty
```

A Go clipboard library called **clippy** explicitly defines:

```go
package main

func main() {
	const SlackDeltaMIME = "slack/texty"

}
```

and describes it as:

> the custom MIME type Slack's composer reads: a Quill Delta document describing the message exactly as its own editor would.

It says that Slack itself puts this representation on the clipboard and that pasting it reconstructs native Slack formatting rather than going through HTML conversion. [Go Packages](https://pkg.go.dev/github.com/neilberkman/clippy%40v1.9.1/pkg/clipboard?utm_source=chatgpt.com)

[clippy clipboard package documentation](https://pkg.go.dev/github.com/neilberkman/clippy/pkg/clipboard?utm_source=chatgpt.com)

That's particularly relevant to you because **it's a Go implementation**, so its source may effectively provide the undocumented specification you need for your Wails application.

Another independent package, `slack-to-markdown`, says the same thing:

> When you copy formatted text from Slack, it stores the content in the `slack/texty` clipboard format.

and demonstrates reading it in a browser paste handler:

```js
document.addEventListener("paste", (e) => {
    const slackData = e.clipboardData?.getData("slack/texty");
});
``` :chatgpt-content-reference{index="2"}


So `slack/texty` isn't merely somebody's guess.

### The macOS/Electron complication

There's an excellent Japanese engineering blog from GO Inc published in January 2026 that specifically reverse-engineered **pasting formatted content into Slack on macOS**.

They concluded that Slack expects:

```text
org.chromium.web-custom-data
```

and that this Chromium container contains MIME/data pairs including:

```text
package main

func main() {
	clipboard.Set("slack/texty", data)

}
```

They describe `slack/texty` as Slack's proprietary JSON format and say the outer `org.chromium.web-custom-data` data is encoded using Chromium's Pickle-like serialisation. [GO Tech Blog](https://techblog.goinc.jp/entry/2026/01/09/132240?utm_source=chatgpt.com)

[GO Tech Blog – Google Docs formatting → Slack clipboard investigation](https://techblog.goinc.jp/entry/2026/01/09/132240?utm_source=chatgpt.com)

That distinction could explain why simply doing something equivalent to:

```go
clipboard.Set("slack/texty", data)
```

at the native macOS level might **not** work.

Chromium/Electron apparently translates web clipboard MIME types into its own macOS pasteboard representation:

```text
NSPasteboard
    │
    └── org.chromium.web-custom-data
             │
             ├── text/plain
             │
             └── slack/texty
                    │
                    └── Quill Delta JSON
```

The clippy Go package independently identifies `org.chromium.web-custom-data` as Chromium's mechanism for transporting web MIME types that don't have native clipboard mappings. [Go Packages](https://pkg.go.dev/github.com/neilberkman/clippy%40v1.9.1/pkg/clipboard?utm_source=chatgpt.com)

### There's also an Obsidian implementation

An Obsidian plugin called **Slack Flavor** deliberately writes three representations:

```text
slack/texty
text/html
text/plain
```

Its documentation says `slack/texty` is written via a browser copy event so Chromium stores it as web custom data. It uses HTML as the interoperability fallback. [Obsidian Stats](https://www.obsidianstats.com/plugins/slack-flavor?utm_source=chatgpt.com)

That is essentially the architecture I'd use in your Wails/WebKit application:

```text
copy
 │
 ├── text/plain
 │      readable fallback
 │
 ├── text/html
 │      generic rich representation
 │
 └── slack/texty
        Slack-native representation
```

The particularly attractive thing about this approach is that the clipboard remains useful in **other applications** rather than becoming Slack-specific.

### HTML works, but there's a gotcha

There are several independent reports that Slack accepts `text/html` / macOS `public.html`.

For example, Aaron Parecki experimented with putting HTML links onto the macOS clipboard. HTML alone didn't work. He discovered that adding a plain-text representation alongside it caused Slack to accept the HTML:

```text
public.html
+
plain text
```

After that Slack pasted the link as formatted content. [aaron.cc](https://aaron.cc/copying-the-current-safari-tab-as-a-to-the-clipboard-as-a-clickable-link/?utm_source=chatgpt.com)

Another Linux user independently hit essentially the same issue. They put only:

```text
text/html
```

on the X11 clipboard. Gmail and HTML editors accepted it, while Slack pasted nothing. Adding:

```text
text/plain
```

alongside `text/html` fixed Slack. [Reddit](https://www.reddit.com/r/firefox/comments/1fsz4sf?utm_source=chatgpt.com)

So I would **not** populate HTML alone.

There's also a recent Cline discussion explicitly proposing:

```text
text/plain
text/html
```

because Slack, Teams and Outlook select the HTML representation and preserve formatting. [GitHub](https://github.com/cline/cline/discussions/10106?utm_source=chatgpt.com)

If your goal is:

I wouldn't concentrate on HTML `<table>` yet.

I'd first investigate the actual structure of a `slack/texty` payload **when Slack itself copies a table**.

The crucial question is whether Slack's newer table editor has an internal Delta representation for rows/cells. If it does, synthesising that could give you **actual Slack table objects**, rather than hoping its HTML importer understands `<table>`.
